# Security Model

## Security objectives

1. A caller can only access data authorized to the corresponding Synology user.
2. Compromise of one user's credential must not expose another user's credential.
3. MCP workers hold no authoritative cross-request user session state.
4. Synology remains the authorization policy enforcement point.
5. The model never receives reusable infrastructure credentials.

## Trust boundaries

```text
[ChatGPT / MCP host]
        |
        | untrusted network
        v
[MCP auth boundary]
        |
        v
[Stateless MCP worker]
        |
        | secret-store API
        v
[Credential store / broker]
        |
        | internal TLS
        v
[Synology DSM / Drive]
```

## Mandatory controls

### Authentication

- Validate issuer, audience, signature, expiry, and required scopes.
- Bind downstream credentials to a stable authenticated subject.
- Reject anonymous access unless an explicit public deployment mode is later designed.

### Authorization

- Never grant file access based solely on a model-provided path.
- Never use an administrative Synology credential as an implicit fallback.
- Rely on Synology's effective user ACL for file authorization.
- Keep caches principal-scoped.

### Secrets

- No secrets in Git.
- No bearer tokens in logs.
- No DSM passwords in normal production configuration.
- Encrypt downstream refresh/session credentials.
- Rotate signing/encryption keys using a documented procedure.

### MCP v2 request state

If `requestState` is used, treat it as untrusted client-carried data.

It must be:

- integrity protected;
- bound to the authenticated principal;
- bound to the originating operation/parameters where practical;
- short-lived;
- rejected after expiry or verification failure.

Do not use `requestState` as a disguised long-lived login session.

### Write operations

Initial releases are read-only.

Before enabling upload/move/delete/share/ACL-changing tools, require:

- explicit threat review;
- audit logging;
- clear confirmation semantics for destructive operations;
- per-user delegated identity proven end to end;
- tests demonstrating that one user cannot mutate another user's resources.

## Threats to test

- principal A reuses a handle created for principal B;
- worker cache leaks A's search result to B;
- token audience confusion;
- stale/revoked Synology credential;
- path traversal or alternate path encoding;
- symlink/alias behavior if filesystem APIs are ever introduced;
- search endpoint returns metadata for inaccessible content;
- malicious document content attempts prompt injection;
- oversized/binary document denial of service;
- credential refresh race across multiple MCP replicas.

## Document-content safety

Files returned by Synology are untrusted content.

The MCP server should distinguish:

- tool metadata generated by the server;
- raw document content;
- instructions contained inside documents.

Document text must never be treated as privileged server instructions.

## Reporting

Until a dedicated security contact is configured, do not publish credentials, tokens, NAS addresses, or reproducible private-environment exploit details in public GitHub issues.
